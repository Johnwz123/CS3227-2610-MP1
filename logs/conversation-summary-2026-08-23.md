## Executive outcome

BudgetBot evolved from a sparse Java coursework starter into a local, single-user
JavaFX budget tracker. The application now has transaction entry and history,
category management, fixed monthly category budgets, a month-focused dashboard,
settings, SQLite persistence, database reset/seed tools, transaction search and
filters, automated quality checks, documentation, and native release packaging.

The principal stack is Java 25, Gradle Wrapper (Gradle 9.7.0), JavaFX, SQLite,
JUnit 6, Mockito, TestFX, Spotless/Google Java Format, Checkstyle, PMD, JaCoCo,
ArchUnit, SpotBugs with FindSecBugs, Docusaurus, GitHub Actions, Dependabot, and
jpackage/jlink. The product deliberately remains local and does not require an
account, cloud synchronization, bank integration, or a paid external service.

The final financial model is explicitly month-focused:

~~~text
Selected-month net cash flow = income in the selected month - expenses in the selected month
~~~

Rollover/carryover and the lifetime Overall balance were removed after discussion.
The dashboard's global Recent activity section was also removed so that the
dashboard does not mix lifetime data with the selected month. Budget tables still
show normal, warning, and over-budget states.

## 1. Starting point and initial project requests

The repository initially contained coursework documentation and a minimal project
scaffold rather than a complete application. The conversation began with requests
to:

1. reorganize the README Technology Stack into suitable subsections;
2. create CONTRIBUTING.md and document Conventional Commits;
3. create a Hello World Java project using the listed tools and configure GitHub
   Actions CI/CD; and
4. set up Docusaurus developer and user guides, published through GitHub Pages.

The starter was implemented with a Java 25 Gradle build, wrapper scripts, a small
Hello World application and tests, and the requested documentation/CI structure.
JUnit Platform launcher configuration was added after the first test execution
showed that the launcher was required. Initial PMD/formatting findings were
addressed rather than ignored. SonarCloud was discussed and removed because the
user did not want a paid service; PIT mutation testing and SLF4J/Logback were
considered but were not added without a concrete need.

## 2. Documentation, CI, and quality-report workflow

The Docusaurus site was placed under website/, with the root README rendered as
the site landing page and separate DeveloperGuide and UserGuide routes. Blank
reflection material was intentionally not published. Node references were
updated from 20 to 24 across the site metadata and workflows. The Linux executable
permission on gradlew was fixed while Windows continued to use gradlew.bat.

JaCoCo reporting was expanded from a single percentage to a reusable Markdown
summary generated by scripts/summarize_jacoco.py. The report includes package and
total instruction, branch, line, complexity, method, and class metrics, including
missed/total counts and percentages. The pull-request coverage comment keeps the
GitHub API call inline because it depends on live Actions context and uses the
stable marker <!-- budgetbot-jacoco-coverage -->; only the transformation logic
was extracted and made locally inspectable.

The repository gained report-opening shortcuts for JaCoCo and Javadoc. A first
attempt using a plain Gradle exec() call failed because the task was not using
the correct process-launching API; the tasks were corrected to use Gradle's
Exec/ExecOperations model. A stale JaCoCo execution-data warning was explained
as stale generated state, not evidence that the application was failing. The
artifact upload action was updated to the Node 24-compatible major version.

## 3. Product implementation and decisions

The Hello World sample was replaced by BudgetBot's local JavaFX application. The
default categories are Housing & Utilities, Groceries, Dining, Transport, Health,
Entertainment, Shopping, Education, and Miscellaneous. Users can add, rename,
and remove categories, with reassignment where required. The main areas are
Dashboard, Transactions, Budgets, and Settings.

Income is positive cash flow and has no expense category. An expense is negative
cash flow and requires a category. Money is represented with BigDecimal; service
validation covers positive transaction amounts, non-negative budgets, two-decimal
precision, valid dates/types/categories/warning thresholds, and valid filter
bounds. SQLite totals are converted into Java monetary values rather than being
handled as unvalidated display strings.

The conversation compared a lifetime Overall balance with a selected-month view.
The user chose Net cash flow for the selected month, defined as that month's
income minus expenses. Rollover/carryover was removed, Recent activity was removed,
and the app was unreleased, so direct schema/model removal was accepted without a
backward-compatibility migration.

The resulting flow is:

~~~text
JavaFX UI -> BudgetService -> BudgetDatabase/repositories -> SQLite
~~~

Month navigation refreshes the current view. Income is shown with a green semantic
cue, expenses with a red cue, and budget rows use normal/warning/over-budget CSS
states rather than redundant status text.

## 4. Architecture and persistence refactoring

The original BudgetBotWindow god file was split into a window shell,
ViewCoordinator, focused views, dialogs, tables, UiAlerts, and MoneyInput.
UI classes were moved into the budgetbot.ui hierarchy. BudgetDatabase became a
facade over CategoryRepository, SettingsRepository, TransactionRepository,
MonthlyBudgetRepository, SchemaInitializer, and shared persistence support.

A null-category mapping defect was fixed by checking ResultSet.wasNull()
immediately after reading nullable category values. Reopen tests were added for
custom categories and settings. Public APIs received @param, @return, and
@throws documentation where applicable, with Javadocs checked by the build.

## 5. Testing, static analysis, and CI enforcement

The test suite covers model, service, persistence, bootstrap, database tools, and
JavaFX UI behavior. TestFX uses ApplicationExtension, FxRobot, and temporary
SQLite databases. Hamcrest is explicit where used; AssertJ was discussed but not
introduced. A navigation race in a UI test was fixed with waitForFxEvents and a
retry around the asynchronous view transition.

The latest recorded local result was 43 passing tests: ArchitectureTest 3,
BudgetBotAppTest 1, ModelTest 4, BudgetDatabaseTest 6, BudgetServiceTest 14,
DatabaseToolTest 4, BudgetBotWindowUiTest 8, and UiSupportTest 3. Historical
JaCoCo metrics were 87.9% instruction coverage, 84.5% line coverage, 76.4% branch
coverage, 85.9% method coverage, and 92.9% class coverage; the configured
instruction threshold is 80%.

ArchUnit rules enforce layer dependencies, model isolation, and the absence of
top-level cycles. The first configuration considered every external dependency
and produced 1,128 false positives. It was corrected to consider only
dependencies in the defined application layers.

SpotBugs with FindSecBugs was added as a real CI quality practice, using maximum
effort and medium confidence. Findings led to try-with-resources for a PRAGMA
statement and parameterized SQL in place of string concatenation. A narrow
EI_EXPOSE_REP2 suppression was retained only where constructor injection was an
intentional service/UI boundary. Groovy enum configuration was corrected to use
Effort.valueOf('MAX') and Confidence.valueOf('MEDIUM'). The final report had
zero SpotBugs/FindSecBugs findings.

## 6. Database tools and repeatable data

PowerShell and POSIX reset/seed scripts were added. Reset requires the literal
RESET confirmation unless Force is used, removes the selected database and
SQLite sidecars, recreates the schema, and restores default settings/categories.
The seed command inserts deterministic current-month sample data and refuses to
duplicate transactions in the same database. The README tells users to close the
app before resetting or seeding.

## 7. Transaction search and filters

The user requested transaction search and filters by date range, category,
income/expense, and amount, with additional suggestions welcomed. The approved
design introduced an immutable TransactionQuery and service validation, with
parameterized SQL and AND semantics across active criteria.

Filtering behavior is:

- description is a case-insensitive substring search;
- start/end dates are inclusive;
- minimum/maximum amounts are inclusive and use exact BigDecimal comparison;
- results are newest first;
- a blank description means no description criterion;
- if no explicit dates are supplied, the selected month is used;
- one-sided date ranges and ranges crossing month boundaries are supported; and
- invalid bounds are rejected without mutating stored data.

The UI gained Apply and Clear actions, a result count, and an empty-state message.
Mutating a transaction refreshes the current results while preserving the active
query. The filter layout was refined in response to the user's screenshot and
follow-up decisions:

- the Income/Expense selector appears before Expense category;
- its minimum width was increased;
- selecting Income clears and hides the expense-category selector;
- selecting an expense category automatically sets Income/Expense to Expense; and
- a responsive FlowPane moves the secondary type/category/amount controls to a
  new row below the description and date controls when the window becomes narrow.

Validation-message presentation required several corrections. The initial label
still clipped long text with an ellipsis, so the transaction dialog replaced it
with a finite-width wrapping TextFlow; the UI test was strengthened to require
at least two rendered lines. Wrapping then pushed Save and Cancel below the dialog,
so validation now requests layout and calls Stage.sizeToScene() after the error
is shown. A UI test compares button scene bounds with the dialog bounds. The same
wrapping and dynamic resizing pattern was applied to the Set budget dialog, with a
slightly wider content area and a dedicated test. These changes ensure the full
message is visible and the dialog buttons remain usable.

The transaction-search OpenSpec change was amended as these UX issues were found.
Its task list progressed from the initial implementation through the responsive
selector behavior and dialog fixes, ending at 31 completed tasks. The delta spec
added two requirements to the main budget-tracking spec: transaction history
search/filtering and filter feedback/recovery, including type/category
coordination, responsive wrapping, complete validation messages, and automatically
resized transaction/budget dialogs.

The change was strictly validated, synchronized into the main spec, and archived
at:

openspec/changes/archive/2026-08-23-add-transaction-search-and-filters/

The final OpenSpec listing had no active changes.

## 8. Native packaging and releases

The release approach selected native installers rather than distributing only a
JAR. jlink/jpackage produce self-contained Windows MSI, macOS DMG, and Debian DEB
artifacts. Tag-triggered GitHub Actions use v<major>.<minor>.<patch>, build a
platform matrix, upload artifacts, and publish a GitHub Release. A missing Bash
fi in the release workflow was corrected.

The conversation distinguished package availability from local build output: users
find completed installers in the workflow artifacts or published GitHub Release.
Hosted macOS ARM TestFX failures involving CGLChoosePixelFormat and modal/pointer
behavior were diagnosed without dropping macOS packaging coverage. Windows and
Ubuntu retain the full gate; macOS performs the supported static/build/package
checks. macOS jpackage rejects a 0.0.4 internal version, so only the internal
DMG package version maps pre-1.0 values to a valid 1.x.y; public tags and asset
names remain unchanged.
